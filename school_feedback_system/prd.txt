School Teacher Feedback & Evaluation System

Product Requirements Document (PRD) and Developer Handoff

Version 1.1  |  2 October 2026  |  Finalized preferences and implementation plan

Purpose: specify a reusable, admin-configurable web application for collecting student feedback about teachers, protecting student privacy, presenting aggregated results, and preserving finalized feedback records.

1. Executive Summary

The system supports multiple academic sessions (for example, 2026–27 and 2027–28). For each session, an administrator imports student and teacher data, maps teachers to classes/sections/subjects and eligible students, creates reusable questionnaire templates, publishes a feedback poll, monitors completion, closes the poll, and generates reports. Students log in using an admission number and see only the teacher–subject feedback cards applicable to them. Teachers can view only aggregated reports about their own teaching. Administrators can view school-wide, question-wise, teacher-wise, subject-wise and class-wise summaries and export reports.

The application must be configurable from its web interface. Routine changes to sessions, questions, rating scales, student/teacher imports, mappings, and poll dates must not require code edits.

2. Product Goals and Non-Goals

Goals

Support Classes 6–12, sections, and optional streams such as Science, Commerce and Humanities.

Support repeatable yearly sessions while preserving historical reports.

Make all routine configuration available through the admin dashboard.

Prevent duplicate student submissions for the same session.

Prevent students and teachers from accessing other users’ private information.

Freeze responses after card submission and prohibit changes to response data after poll closure.

Provide reliable aggregates, visualizations, and individual or bulk exports.

Keep an audit trail for privileged actions and lifecycle changes.

Non-goals for the first release

No public teacher leaderboard or ranking by default.

No student-level feedback disclosure to teachers.

No automated disciplinary decisions based solely on ratings.

No requirement for AI-generated judgments about teacher performance.

No promise of absolute anonymity: the system can reduce identifiability, but small groups and technical logs may still permit inference.

FINALIZED LOGIN DECISION — Student login uses admission number only, as requested. Security implication: admission number is an identifier, not a secret. Anyone who knows another student’s number may impersonate them. Mitigations for this lower-assurance mode: rate-limit attempts, apply progressive cooldowns, use generic errors that do not confirm whether an admission number exists, restrict the poll window, monitor suspicious attempt patterns, and use a school-supervised launch where feasible. These controls reduce abuse but do not provide strong identity verification. The school must explicitly accept this residual risk before production. Teacher login uses teacher ID, registered phone number and date of birth as requested. These are personal details and may be guessable or known to others; apply rate limits, generic errors, limited retries, avoid displaying full phone numbers, protect date-of-birth data, and document that this is lower assurance than a verified OTP or password. If the school later permits it, add an optional second verification factor.

4. Main User Journeys

4.1 Session setup and administration

Admin signs in securely and creates a session with a unique name, such as 2026–27, plus start/end dates and status.

Admin uploads the student Excel file and teacher Excel file separately.

The system previews rows, validates required columns, detects duplicates and missing fields, and displays an import summary before committing.

Admin fixes errors in the dashboard or downloads an error file, then confirms the import.

Admin maps each teacher to one or more class/section/subject combinations and selects the students who actually study that subject with that teacher.

Admin creates or reuses questionnaire templates and assigns them to the relevant teacher groups or individual teacher–subject assignments.

Admin previews the complete student experience, checks coverage and launches the poll.

Admin monitors participation counts without seeing student answers tied to identities.

At the deadline, admin closes the poll. The closed state becomes irreversible through normal application controls.

Admin generates, reviews and exports reports. The session remains available as read-only history.

4.2 Teacher–subject mapping

Choose session → class → section → subject → teacher.

Show a searchable list of students in that class/section; include Select All, clear selection, selected count, and bulk selection.

Support stream/filter fields for Classes 11–12 when available in the imported student data.

Allow mapping every student in a class to a subject in one action, then permit exclusions or individual selection.

Validate that selected students belong to the chosen session/class/section.

Support one teacher teaching multiple classes and multiple subjects; support multiple teachers teaching the same subject to different student groups.

Show a mapping review screen and detect accidental overlaps or missing assignments before publication.

4.3 Questionnaire builder

Google Forms-like builder: add, edit, delete, reorder and duplicate questions using a simple interface.

Question types: 1–5 rating, custom labeled scale, single choice, multiple choice, and optional text response if the school permits it.

Configure labels (for example, 1 = Needs Improvement and 5 = Excellent), required/optional status, help text, and question category.

Create reusable templates for Academic Teachers, Sports Department, Computer/IT, Activity Teachers, and other categories.

Assign a template to a teacher category, subject, class, individual teacher, or specific teacher–subject mapping.

Define precedence when assignments overlap: most-specific assignment wins; the admin preview must show the final question set.

After the poll launches, questionnaire content and mappings are locked. Any needed correction must be handled before launch; no response-affecting edits after launch.

4.4 Student feedback

Student enters admission number and completes the configured verification step.

The server checks that the student exists in the active session and has not already completed the session.

The dashboard shows only the student’s assigned teacher–subject cards. Each card displays teacher display name, subject, class/section context where useful, and completion status.

Student opens a card, answers the configured questions, and reviews answers before finalizing that card.

On card finalization, answers are saved atomically and the card becomes read-only.

Student proceeds through the remaining cards. Progress is shown without revealing results.

After all required cards are finalized, the student submits the overall feedback record.

The server atomically marks the session submission complete and prevents any further submission for that admission number in that session.

A clear success screen appears, with a friendly animation such as subtle balloons/confetti, plus a confirmation message.

Important clarification: if a student closes the browser halfway through, already finalized cards remain locked. The system should let the student resume only the unfinished cards until the overall submission is complete. If the intended policy is to lock the entire student record after the first card instead, that should be confirmed before implementation.

5. Session and Poll Lifecycle

State

Allowed actions

Restrictions

Draft

Edit session data, imports, mappings, questions and templates.

Not visible to students.

Ready for review

Preview, run validation, fix issues, approve configuration.

No submissions yet.

Live

Students submit; admin monitors counts; teachers normally cannot view live results.

Configuration affecting responses is locked.

Closed

Read reports and export; inspect audit history.

No new submissions, edits, deletes or reopening through UI/API.

Archived

Read-only historical access under retention policy.

No ordinary data mutations.

FINALIZED POLL-OFF POLICY — Once the poll is switched off/closed, the application becomes read-only for feedback data. Students cannot submit new votes, change answers, or finalize unfinished feedback; administrators cannot edit, add, delete, or overwrite votes. Reports remain available for viewing and authorized downloading only. Ordinary admin controls cannot reopen the poll. If an exceptional recovery process is ever approved, it must not mutate the closed poll or its votes; the preferred path is a separately authorized new poll/version with a written reason and immutable audit event, while the original poll and reports remain preserved. Enforce closure in backend service logic and database permissions, not merely by hiding buttons. Use finalized response records, database constraints, an audit event, backups and a closure snapshot/hash to make tampering detectable. Encryption alone does not make data immutable, and no application can honestly guarantee that a sufficiently privileged infrastructure owner can never alter or delete data.

6. Reports and Analytics

6.1 Teacher portal

Landing page with an overall summary for the teacher’s assigned classes/subjects.

Cards or tabs for each class/section, plus an Overall Report view.

Each report shows response count, eligible count or participation percentage where disclosure is safe, average score by question, and distribution of ratings.

Filters: session, class, section, subject, questionnaire category and question.

Do not show student names, admission numbers, individual response rows, or timestamps that could identify students.

Apply a minimum group-size threshold (configurable, recommended default at least 5 responses) before showing granular results. Suppress or combine smaller groups.

6.2 Admin portal

School overview: eligible students, submitted students, participation rate, teacher/subject coverage and poll status.

Question comparison: for each common question, show average score per teacher using the same question and scale.

Teacher profile report: question-wise and subject-wise results for one teacher, with class/section breakdowns.

Class report: rows grouped by class and section; columns include teacher, subject and each question’s average rating.

Subject report: compare assigned teacher groups for the same subject and question set.

Whole-school report: aggregated distributions and averages with clear explanation of which groups are included.

Visualizations: bar charts, stacked rating distributions, response-rate charts and trends across sessions when comparable questions/scales exist.

Exports: one teacher report, selected teachers, one class/section, one subject, whole-school report, and bulk ZIP or workbook export.

Comparisons must only compare equivalent questions with the same scale and compatible assignment context. Show response count and suppression notes alongside averages. Do not present a numeric average as a complete or objective measure of teacher quality, and do not create public leaderboards by default.

7. Import Templates and Validation

Student spreadsheet — suggested columns

Required: admission_number, student_name, class, section. Optional: stream, roll_number, status, school_email or approved verification field. Keep admission numbers as text to preserve leading zeroes.

Teacher spreadsheet — suggested columns

Required: teacher_id, teacher_name. Optional: phone_number, date_of_birth (only if justified and access-restricted), email, department/category, active_status, subjects_taught. Prefer a separate teacher-subject table for teachers with multiple subjects.

Support .xlsx and .csv; show a column-mapping screen if uploaded headers differ.

Reject or flag missing required fields, duplicate IDs, invalid classes/sections, and malformed contact values.

Provide a preview, row counts, downloadable error report, and confirmation before importing.

Use stable internal IDs; do not rely on names as unique identifiers.

Define whether re-import updates existing records or creates a new version; require an explicit choice and show the impact.

Do not silently overwrite live-session mappings or historical session records.

9. Security, Privacy and Integrity Requirements

Enforce authorization on every server endpoint; UI hiding alone is not security.

Use secure password hashing for admin accounts, secure session cookies, CSRF protection where relevant, rate limiting, and login throttling.

Use an additional verification factor for students where feasible; admission number alone is not secure authentication.

Teacher authentication should not rely only on teacher ID, phone number and date of birth. Add OTP or another verified factor and protect contact data.

Encrypt traffic with HTTPS and encrypt sensitive data at rest using managed keys where available.

Keep identity/eligibility records separate from feedback answers. Avoid storing student ID, name, IP address or unnecessary identifiers alongside response rows.

Do not log answers or authentication secrets. Restrict and time-limit access to operational logs.

Use database transactions and unique constraints to prevent duplicate card and session submissions under simultaneous requests.

Finalize a card in one atomic server operation. Reject all later edits, including direct API requests.

On closure, enforce read-only behavior at service and database permission layers; create an audit event and a verifiable closure snapshot.

Use regular encrypted backups, restore testing, restricted administrator access, dependency updates and security testing.

Protect exports with authorization, expiry or access controls; avoid public URLs and avoid putting student data in filenames.

Set a retention/deletion policy, access policy, school-approved privacy notice, and incident-response process before launch.

Collect only data required for the workflow. Date of birth and personal phone number should not be imported unless the school confirms a valid need.

Security limitation: encryption protects confidentiality; it does not by itself prevent an authorized operator from changing data. A closed poll should be treated as tamper-evident and operationally immutable, with limited privileged access and an audit trail, rather than claiming mathematically absolute immutability.

Responsive UI works on common mobile screens; controls are keyboard accessible and labels are readable.

11. Recommended Technical Architecture

FINALIZED TECHNOLOGY AND DEPLOYMENT — Use Python + Streamlit on the school local network, with PostgreSQL recommended for multi-user use. SQLite is acceptable only for a local prototype or small controlled pilot after concurrency limitations are understood. Keep business logic in testable modules separate from Streamlit pages. Streamlit session state is temporary UI state only; the database is the source of truth for authentication attempts, eligibility, card finalization, poll status and permissions. Enforce authorization on every server-side read/write operation. Bind the service to the school network only, restrict inbound network access with firewall rules, use named staff accounts and least-privilege access, keep the host machine physically and logically secured, and schedule encrypted backups. If users access over Wi-Fi or any untrusted shared network, use HTTPS even on the local network. Define who patches the host and restores backups.

Frontend: responsive admin, student and teacher portals; role-specific navigation.

Backend: authenticated API/server views, role-based permissions, validation, report calculations and export generation.

Database: PostgreSQL for production; SQLite may be acceptable for a controlled prototype but not as the default multi-user production deployment.

Imports: pandas/openpyxl or equivalent for spreadsheet parsing, with validation before database writes.

Exports: XLSX and PDF initially; CSV for data interchange; ZIP for bulk exports.

Charts: a maintained charting library with accessible labels and downloadable data.

Deployment: HTTPS, environment-based secrets, managed backups, database migrations, staging environment and documented recovery process.

13. Essential Test Scenarios

An unknown admission number cannot see feedback cards. Repeated invalid attempts are throttled and do not reveal whether an admission number exists.

A student cannot see cards assigned to another class, section or teacher.

An admission number cannot complete the same session twice, including concurrent requests or refreshes.

A finalized card cannot be changed by browser navigation, API calls or another device.

An incomplete student can resume unfinished cards without editing completed ones.

A teacher cannot access another teacher’s report by changing a URL or request parameter.

A teacher report never contains student names, admission numbers or individual answer rows.

Small-group reports are suppressed below the configured threshold.

Changing a questionnaire after launch is blocked; existing responses keep their original question version.

Closing the poll blocks all new writes immediately, even if a student left a form open before closure. Emergency recovery requires separate authorization and leaves an immutable audit event; the original closure and responses remain preserved.

Bulk exports respect role permissions and filters and do not leak hidden fields.

Backup restoration preserves finalized responses, closure state and audit history.

Invalid Excel imports do not partially corrupt or silently overwrite existing data.
